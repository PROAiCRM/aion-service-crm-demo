# MP-002 Mobile Express Intake — Minimum Data & Flow Policy v0.1

**Статус:** PRODUCT POLICY DESIGNED — NOT IMPLEMENTED  
**Дата:** 2026-08-01  
**Применяется к:** MP-002 Mobile Express Intake

## 1. Цель

Определить минимальный набор данных и самый короткий безопасный поток, который позволяет создать исполнимый и доказуемый заказ без превращения Express Intake в урезанную копию полной CRM.

Принцип:

> Каждое обязательное поле должно либо защищать клиента/бизнес, либо быть необходимо для исполнения заказа. Всё остальное откладывается.

## 2. Критерий «полноценной приёмки»

Заказ считается полноценно оформленным в MP-002, когда одновременно существуют:

- установленный tenant и actor из серверной сессии;
- идентифицируемый канал связи с клиентом;
- устройство или честный статус `модель уточняется`;
- основная проблема/услуга;
- зафиксированная цена, диапазон или режим `после диагностики`;
- срок или режим срока;
- понятная версия условий;
- подтверждение клиента, когда оно обязательно;
- один созданный service order;
- одна intake receipt;
- один command receipt;
- безопасный следующий шаг для клиента и сотрудника.

Красивый экран без этих объектов не считается полноценной приёмкой.

## 3. Классы данных

### D0 — серверный контекст, не вводится вручную

- `organization_id`;
- `actor_user_id`;
- `membership/role`;
- session/AAL context;
- created timestamp;
- source `MOBILE_EXPRESS`;
- idempotency identity.

Клиент не может подменять эти поля в request body.

### D1 — обязательный минимум

- основной контакт клиента;
- устройство или статус неопределённой модели;
- основная проблема/услуга;
- цена/диапазон/режим цены;
- срок/режим срока;
- consent state;
- версия условий.

### D2 — условно обязательные

Требуются только при конкретном типе ремонта или политике:

- имя клиента;
- цвет устройства;
- комплектность;
- видимые повреждения;
- пароль устройства — по умолчанию запрещён, отдельная безопасная процедура;
- серийный номер/IMEI — не используется без доказанной необходимости;
- предоплата;
- выбранная запчасть;
- гарантийный режим.

### D3 — необязательные улучшения

- комментарий клиента;
- альтернативный контакт;
- предпочтительный канал связи;
- источник обращения;
- маркетинговое согласие;
- фото состояния при отдельной политике.

D3 не должен блокировать создание заказа.

## 4. Контакт клиента

### Рекомендуемый MVP

Основной контакт — телефон, нормализованный сервером.

Правила:

- допускается ввод `+7`, `8`, десяти цифр и форматированного номера;
- UI показывает исходно понятный формат;
- сервер хранит нормализованное значение по принятой модели;
- поиск существующего клиента выполняется tenant-safe;
- совпадение телефона не должно автоматически объединять клиентов без понятного действия;
- при отсутствии телефона используется только отдельно утверждённый альтернативный сценарий.

### Запрещено

- выводить существующие контакты другого tenant;
- создавать клиента на каждый повторный ввод без проверки;
- использовать телефон как публичный QR-secret;
- помещать полный телефон в Evidence;
- требовать маркетинговое согласие для ремонта.

## 5. Имя клиента

Имя может быть:

- обязательным коротким именем;
- необязательным в самом быстром потоке;
- автоматически предложенным из существующей карточки.

Решение принимается по данным пилота: если отсутствие имени мешает выдаче и поиску, оно становится обязательным; если сотрудники вводят мусор ради скорости, поле пересматривается.

Нельзя заставлять вводить полные паспортные данные без отдельной юридической необходимости.

## 6. Устройство

### Допустимые состояния

1. Точная модель подтверждена сотрудником.
2. Выбрана модель из нескольких вероятных вариантов.
3. Известны бренд/линейка, модель уточняется.
4. Устройство описано безопасным общим названием, если точность не нужна для приёмки.

### Инварианты

- camera assist не записывает модель как факт без подтверждения;
- неизвестная модель не должна превращаться в заведомо ложную;
- изменение модели после создания фиксируется как корректировка;
- модель связана с общим device core, а не отдельной Express-таблицей;
- клиентская квитанция не показывает внутренние идентификаторы.

## 7. Проблема и услуга

В первом MVP сотрудник выбирает одну основную услугу или причину обращения.

Если нужны несколько работ:

- сохраняется минимальный intake;
- открывается полный Order Workspace;
- клиенту показывается, что итоговый состав будет уточнён;
- запрещены скрытые дополнительные работы.

Каталог услуги должен показывать минимум:

- название;
- цену или диапазон;
- срок;
- гарантию, если подтверждена;
- доступность/ограничение, если данные надёжны.

## 8. Модель цены

Допустимы три режима:

### FIXED

Цена согласована как фиксированная для указанного объёма.

### RANGE

Клиент видит нижнюю и верхнюю границу, а также условие уточнения.

### AFTER_DIAGNOSTICS

Указывается стоимость диагностики, если есть, и необходимость отдельного согласования ремонта.

Запрещено:

- подставлять неактуальную цену без обозначения;
- скрывать, что цена предварительная;
- сохранять пустое число как `0`;
- автоматически повышать цену после подписи;
- смешивать себестоимость и клиентскую цену.

## 9. Модель срока

Допустимы:

- точное подтверждённое время;
- диапазон;
- дата;
- `после диагностики`;
- `уточняется`.

UI обязан отличать обещание от ориентира.

AI не создаёт срок как факт.

## 10. Комплектность и состояние

Для стандартного экспресс-ремонта допускается короткий checklist:

- устройство;
- SIM/чехол/кабель — только если переданы;
- экран/корпус: без подробностей либо краткий выбор;
- включается/не включается;
- дополнительные видимые дефекты.

Расширенная фиксация открывается только при необходимости.

Нельзя заставлять сотрудника проходить длинный осмотр для простой услуги, если это уничтожает двухминутную цель.

## 11. UX-поток

### Экран 1 — Клиент и устройство

- телефон;
- существующий клиент или новый;
- ручной поиск устройства;
- дополнительная кнопка камеры;
- модель подтверждается человеком.

### Экран 2 — Работа и условия

- одна услуга;
- цена/режим;
- срок/режим;
- короткие риски/условия.

### Экран 3 — Согласие и создание

- клиент видит итог;
- подтверждает установленным способом;
- одна CTA `Оформить ремонт`;
- двойной tap блокируется;
- состояние отправки честно отображается.

### Экран результата

- один заказ;
- номер;
- receipt readiness;
- QR/ссылка при доступности;
- `Открыть заказ`;
- исправление только через контролируемый edit flow.

Количество экранов может быть визуально объединено, но смысловые этапы сохраняются.

## 12. Черновик

Черновик может хранить:

- введённые поля;
- локальный progress;
- выбранную услугу;
- безопасную pending mutation identity.

Правила:

- не хранить подпись и фото камеры в обычном localStorage;
- установить срок жизни;
- привязать к tenant/user context;
- очищать использованный черновик только после доказанного успеха;
- при logout удалять или блокировать доступ;
- не синхронизировать без отдельного offline design.

## 13. Ошибки и восстановление

### Детерминированная ошибка до commit

Показать поле/причину, сохранить черновик, разрешить исправление.

### Результат неизвестен

Показать:

> «Ответ не получен. Проверяем, был ли заказ создан. Не оформляйте повторно.»

Использовать ту же idempotency identity и reconciliation.

### Заказ создан, документ не готов

Заказ остаётся созданным. UI не создаёт второй заказ. Показать отдельный статус документа и действие повторной подготовки.

### Камера недоступна

Перейти к ручному поиску без блокировки.

### Consent interrupted

Не создавать ложное согласие. Вернуть к итоговым условиям.

## 14. Серверная валидация

Клиентская форма не является границей доверия.

Сервер проверяет:

- actor/tenant из сессии;
- permissions;
- обязательные поля;
- формат контакта;
- допустимый price/deadline mode;
- catalog/tenant ownership;
- consent contract version;
- idempotency key;
- отсутствие client-supplied organization/role/owner confirmation;
- transaction invariants.

## 15. Data-quality guardrails

Пилот останавливается или сужается при:

- частых исправлениях клиента;
- ошибочной модели устройства;
- несогласованной цене;
- заказах без реальной услуги;
- массовом выборе `другое`;
- фальшивых номерах ради ускорения;
- пропущенном consent;
- большом количестве незавершённых черновиков.

## 16. Тестовые сценарии

- новый клиент + ручная модель;
- существующий клиент + существующее устройство;
- неизвестная модель;
- одна услуга FIXED;
- RANGE;
- AFTER_DIAGNOSTICS;
- несколько работ → полный заказ;
- двойной tap;
- reload до ответа;
- lost response after commit;
- validation failure;
- consent refusal;
- camera denied;
- offline/poor network;
- cross-tenant catalog/device attempt;
- employee without permission.

## 17. Решения v0.1

- одна основная услуга в Express MVP;
- минимальные данные важнее полноты CRM-карточки;
- неизвестная модель допустима, ложная — нет;
- камера необязательна;
- цена и срок имеют явные режимы;
- consent связан с версией итоговых условий;
- один логический submit создаёт один заказ;
- расширение формы допускается только после Evidence.

## 18. Открытые Owner Gates

- обязательность имени;
- набор обязательной фиксации состояния;
- разрешённые типы ремонта для пилота;
- допустимые режимы цены;
- допустимый способ согласия;
- использование серверной обработки камеры;
- срок хранения черновика;
- печать по умолчанию или QR-first handoff.
