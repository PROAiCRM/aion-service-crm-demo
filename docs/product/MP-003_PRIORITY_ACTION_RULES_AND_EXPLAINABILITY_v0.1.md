# MP-003 Owner Pulse — Priority Action Rules & Explainability v0.1

**Статус:** DESIGNED — DETERMINISTIC FIRST  
**Дата:** 2026-08-01

## 1. Цель

Определить, как Owner Pulse выбирает ровно одно главное действие без недоказанного AI, скрытых весов и обвинения сотрудников.

## 2. Принцип

Первая версия использует только детерминированные правила:

```text
verified facts → eligible actions → priority ordering → one recommendation → explanation
```

Recommendation engine не изменяет заказы, платежи, сроки или сотрудников.

## 3. Candidate actions MVP

1. Связаться с клиентом по просроченному согласованию.
2. Проверить завершённый заказ с долгом перед выдачей.
3. Уточнить просроченное обещание и назначить владельца следующего шага.
4. Организовать выдачу готового устройства, которое долго ждёт клиента.
5. Проверить конфликт или неполноту данных, если Owner Pulse не может доверять показателю.

## 4. Hard priority tiers

### P0 — Trust and safety

- cross-source conflict;
- data-quality `CONFLICT` для денег;
- tenant boundary anomaly;
- неизвестный результат критической денежной операции;
- скрытая write-side effect обнаружена в read path.

P0 всегда выше операционных рекомендаций. Формулировка нейтральная: «Проверьте данные», а не «Сотрудник допустил нарушение».

### P1 — Money already earned but at risk

- готовый/завершённый заказ с долгом;
- выдача с долгом без подтверждённого исключения;
- неразрешённое расхождение платежей.

### P2 — Broken customer promise

- подтверждённый срок истёк;
- нет актуального пересогласования;
- заказ активен.

### P3 — Customer blocking flow

- долгое ожидание согласования;
- готовый заказ долго не выдан;
- требуется информация клиента.

### P4 — Operational improvement

- менее срочные действия, которые уменьшают очередь или задержку.

## 5. Ordering inside tier

Внутри уровня используется прозрачный порядок:

1. длительность риска;
2. подтверждённая сумма долга — только для денежных действий;
3. близость к необратимому событию, например выдаче;
4. число затронутых заказов;
5. стабильный tie-breaker по времени создания и безопасному идентификатору.

Нельзя использовать скрытый «employee risk score».

## 6. Required explanation

Каждая рекомендация отвечает:

- **Что сделать?**
- **Почему сейчас?**
- **Какие факты использованы?**
- **Насколько свежи данные?**
- **Что изменится после действия?**
- **Почему другие действия ниже?** — кратко по tier.

Пример:

> Свяжитесь с клиентом по заказу SO-0124. Подтверждённый срок истёк 2 часа назад, заказ ждёт согласования 6 часов. Данные обновлены 40 секунд назад. Правило `PROMISE_OVERDUE_V1`, приоритет P2.

## 7. Action lifecycle

- `ACTIVE` — рекомендация актуальна;
- `OPENED` — владелец открыл объект;
- `COMPLETED` — подтверждённое действие выполнено;
- `DISMISSED` — владелец отклонил с причиной;
- `EXPIRED` — факты изменились;
- `SUPERSEDED` — появилось действие более высокого уровня.

Нельзя считать клик выполнением действия.

## 8. Dismiss reasons

Allowlist MVP:

- `ALREADY_HANDLED`;
- `NOT_RELEVANT`;
- `DATA_WRONG`;
- `WAITING_FOR_EXTERNAL_EVENT`;
- `OWNER_CHOSE_OTHER_PRIORITY`;
- `OTHER_WITH_NOTE`.

Причины используются для улучшения правил, а не оценки сотрудника.

## 9. No-action state

Если нет доказанного действия, экран показывает:

> Критичных действий по текущим проверенным данным нет.

Запрещено создавать рекомендацию ради заполнения карточки.

## 10. AI boundary

AI может позже:

- сократить техническое explanation;
- объединить близкие факты;
- предложить текст звонка или сообщения после выбора человеком;
- проанализировать причины dismiss на агрегированном уровне.

AI не может:

- менять tier;
- подменять факты;
- придумывать денежный эффект;
- автоматически выполнять действие;
- формировать обвинение;
- скрывать rule ID и уровень уверенности.

## 11. Test matrix

- P0 всегда выше P1–P4;
- P1 выше просрочки при равных условиях;
- stale/conflict facts не создают обычную action recommendation;
- одинаковый набор фактов всегда даёт одинаковое действие;
- изменение факта инвалидирует старую рекомендацию;
- cross-tenant объект не может стать candidate;
- no eligible candidates → no-action state;
- tie-break deterministic;
- объяснение содержит rule version и timestamp;
- dismissed action не исчезает из Evidence, но не блокирует новое более приоритетное действие;
- AI отключён — функциональность сохраняется полностью.

## 12. Stop criteria

Остановить рекомендации, если:

- владелец часто выбирает `DATA_WRONG`;
- правило создаёт конфликт с реальным workflow;
- действие невозможно завершить из Owner Pulse;
- recommendation зависит от недоказанной суммы;
- появляется давление или обвинительная формулировка;
- правила становятся сложнее, чем операционная польза.
