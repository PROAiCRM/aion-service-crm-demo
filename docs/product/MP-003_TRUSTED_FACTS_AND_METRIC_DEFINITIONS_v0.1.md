# MP-003 Owner Pulse — Trusted Facts & Metric Definitions v0.1

**Статус:** DESIGNED — NOT IMPLEMENTED AS A UNIFIED READ MODEL  
**Дата:** 2026-08-01

## 1. Цель

Закрепить точные определения пяти фактов Owner Pulse, чтобы интерфейс не смешивал кассу, выручку, долг, прибыль, просрочку и ожидание клиента.

## 2. Базовое правило истины

Owner Pulse не создаёт собственную параллельную истину. Он читает данные из существующих источников modular monolith и формирует версионированную owner-facing projection.

Каждый показатель обязан иметь:

- semantic ID;
- формулу или правило;
- источник данных;
- временную зону;
- as-of timestamp;
- freshness state;
- data-quality state;
- drill-down до объектов;
- версию определения.

## 3. Денежные понятия

### 3.1 `cash_received_today`

**Определение:** сумма успешно проведённых входящих платежных операций организации за текущий операционный день.

Включается:

- наличная оплата;
- безналичная оплата;
- частичная оплата;
- аванс;
- доплата;
- окончательный платёж.

Не включается:

- ожидаемый платёж;
- стоимость созданного заказа;
- сумма согласованного ремонта без оплаты;
- возврат, если он не учтён отдельным знаком/операцией;
- отменённая или неуспешная транзакция;
- прибыль;
- движение денег другого tenant.

Формула должна учитывать знак и тип операции. Если возвраты ведутся отдельным типом, UI показывает gross received и refunds/net отдельно либо использует утверждённое net-правило.

### 3.2 Запрещённые подмены

Нельзя подписывать `cash_received_today` как:

- «выручка», если система не определила выручку;
- «прибыль»;
- «заработано»;
- «касса», если в показатель не входят остатки кассовой смены.

Базовая подпись MVP: **«Получено сегодня»**.

## 4. `completed_unpaid_orders`

**Определение:** заказы в подтверждённом состоянии готовности/завершения, по которым расчётный остаток к оплате положителен.

Необходимые факты:

- chargeable total по действующей версии заказа;
- сумма успешных платежей с учётом возвратов;
- допустимый статус заказа;
- валюта и правила округления.

Условия включения:

```text
order is READY or COMPLETED
AND amount_due > tolerance
AND not cancelled
AND tenant matches current organization
```

`amount_due` не должен вычисляться из UI-кеша или старого snapshot, если источник истины изменился.

## 5. `overdue_orders`

**Определение:** активные заказы, у которых подтверждённое обещание клиенту истекло, а заказ не перешёл в состояние, оправдывающее исключение по утверждённому правилу.

Обязательные поля:

- обещанный срок и его источник;
- версия обещания;
- timezone;
- текущий статус;
- причина паузы;
- время последнего пересчёта.

Нельзя считать просрочкой:

- внутреннюю цель сотрудника, не сообщённую клиенту;
- автоматически угаданный ETA;
- пустой срок;
- заказ, где срок был корректно пересогласован и новая версия подтверждена;
- закрытый отменённый заказ, если политика не требует отдельного контроля.

### Производный статус

Если dashboard вызывает `app.refresh_promise_status`, это write-side effect. В MVP должен быть принят один из вариантов:

1. производный статус обновляется отдельно по событию/плановому процессу, а Owner Pulse только читает;
2. Owner Pulse вычисляет статус в read projection без изменения бизнес-таблиц;
3. явная mutation маркируется и не маскируется под read-only запрос.

Скрытая запись при просмотре запрещена.

## 6. `waiting_for_client_orders`

**Определение:** активные заказы, дальнейшее движение которых зависит от конкретного подтверждённого действия клиента.

Разрешённые причины MVP:

- `APPROVAL_REQUIRED` — нужно согласование цены/работы;
- `INFORMATION_REQUIRED` — нужны данные клиента;
- `PAYMENT_REQUIRED` — требуется оплата по утверждённой политике;
- `PICKUP_REQUIRED` — устройство готово и ждёт выдачи;
- `CLIENT_RESPONSE_REQUIRED` — требуется ответ по ограниченному вопросу.

Каждая причина должна иметь:

- время начала ожидания;
- последнее действие сервиса;
- следующий допустимый шаг;
- связь с заказом;
- критерий выхода из ожидания.

Общий статус `waiting_client` без причины недостаточен для управленческого решения.

## 7. `top_priority_action`

Это не число, а детерминированная рекомендация.

Обязательные поля:

- `action_type`;
- `object_type` и безопасная ссылка на объект;
- `reason_code`;
- `reason_text`;
- `rule_version`;
- `evidence_summary`;
- `generated_at`;
- `valid_until` или условие актуальности;
- `dismissed_reason`, если владелец отклонил действие.

Рекомендация не должна содержать invented money impact.

## 8. Data-quality states

Каждый показатель получает один из статусов:

- `TRUSTED` — источники полны, свежи и прошли проверки;
- `PARTIAL` — часть данных отсутствует, значение может быть неполным;
- `STALE` — данные старше допустимого окна;
- `CONFLICT` — источники расходятся;
- `UNAVAILABLE` — значение нельзя безопасно вычислить.

`PARTIAL`, `STALE`, `CONFLICT` и `UNAVAILABLE` нельзя отображать как обычный ноль.

## 9. Freshness

Рабочие начальные пороги:

- платежи: не старше 60 секунд при доступном runtime;
- операционные статусы: не старше 2 минут;
- производные обещания: timestamp последнего расчёта обязателен;
- offline mode: явно показывает время последней синхронизации.

Пороги должны быть проверены на реальной локальной инфраструктуре и слабом Wi‑Fi.

## 10. Тестовые инварианты

- сумма платежей совпадает с ledger/source query;
- возврат не увеличивает полученные деньги;
- отменённый платёж не учитывается;
- частичный платёж формирует правильный долг;
- изменение цены обновляет долг по действующей версии;
- пустое обещание не становится просрочкой;
- пересогласованный срок заменяет старый только после доказанного подтверждения;
- waiting reason не сохраняется после выполнения действия клиента;
- cross-tenant записи отсутствуют;
- неизвестное значение не превращается в ноль;
- timezone boundary на смене даты проверена;
- drill-down count равен показанному aggregate.

## 11. Change control

Любое изменение определения требует:

- новой semantic version;
- regression tests;
- описания влияния на исторические сравнения;
- обновления Owner Pulse tooltip/description;
- записи в Decision Log;
- запрета тихого пересчёта старых Evidence по новой формуле.
