# MP-001 Smart QR Status — Access Model & Threat Decision v0.1

**Статус:** PROPOSED SECURITY DECISION — OWNER GATE PENDING  
**Дата:** 2026-08-01  
**Продукт:** MP-001 Smart QR Status  
**Решение для первого контролируемого пилота:** высокоэнтропийная отзывная bearer-ссылка без короткого кода  
**Важно:** это проектное решение. Оно не разрешает включение реальных клиентских ссылок или развёртывание Draft source.

## 1. Вопрос решения

Как клиент должен получить доступ к публичному статусу ремонта так, чтобы:

- страница открывалась быстро с телефона;
- не требовались регистрация и employee session;
- заказ нельзя было подобрать перебором;
- утёкшую или потерянную ссылку можно было отозвать;
- токен не хранился открыто в базе, snapshots, событиях и логах;
- печатный QR не становился устаревшим после перевыпуска;
- безопасность не уничтожала первую клиентскую ценность дополнительными шагами.

## 2. Рассмотренные варианты

### Вариант A — высокоэнтропийная bearer-ссылка

Клиент сканирует QR и сразу открывает страницу. Владение ссылкой даёт доступ к ограниченной публичной проекции.

**Плюсы:**

- один шаг;
- минимальная поддержка;
- подходит для печатной квитанции;
- нет короткого секрета, который удобно перебирать;
- простая модель для клиента.

**Риски:**

- человек, получивший фотографию квитанции или ссылку, может открыть статус;
- ссылка может остаться в истории браузера;
- требуется строгая защита логов, cache и referrer;
- важны отзыв, версия и срок жизни.

### Вариант B — bearer-ссылка плюс короткий код

После открытия ссылки клиент вводит код с квитанции или отдельного сообщения.

**Плюсы:**

- фотография только QR или только кода недостаточна;
- дополнительный барьер при случайном раскрытии ссылки.

**Риски:**

- клиенту нужно выполнить дополнительное действие;
- код забывают, теряют и диктуют сотруднику;
- нужен rate limiting и защита от перебора;
- короткий код имеет существенно меньшую энтропию;
- растёт число обращений «не могу войти»;
- QR и код часто находятся на одном листе, поэтому защита может быть иллюзорной;
- появляется ещё один секрет и жизненный цикл.

### Вариант C — вход по телефону/одноразовому коду

Клиент подтверждает номер телефона через SMS или другой канал.

**Плюсы:**

- доступ связывается с подтверждённым каналом клиента;
- можно строить более широкий личный кабинет.

**Риски:**

- внешний провайдер и стоимость сообщений;
- зависимость от связи;
- обработка номера телефона;
- более сложный auth/recovery контур;
- продукт перестаёт быть мгновенным QR-статусом;
- повышается критичность отказа провайдера.

### Вариант D — открытие по номеру заказа и телефону

Клиент вводит известные данные.

**Плюсы:**

- нет отдельного QR-секрета;
- понятный fallback.

**Риски:**

- номер заказа может быть последовательным;
- телефон является персональным идентификатором;
- повышается риск enumeration;
- телефон попадает в публичный auth boundary;
- хуже privacy и поддержка форматов номера.

## 3. Рекомендуемое решение

Для первой контролируемой версии рекомендуется **вариант A**:

> Высокоэнтропийная, отзывная и версионируемая bearer-ссылка, представленная QR-кодом и безопасным URL, без дополнительного короткого кода.

Причина выбора: она лучше всего сохраняет First-Value Moment — клиент получает статус сразу после сканирования — и не добавляет слабый короткий секрет, который требует отдельной защиты и поддержки.

Это решение допустимо только при строгом ограничении публичных полей. Bearer-ссылка не должна открывать персональные данные, внутреннюю диагностику, IMEI, серийный номер, пароли, сотрудников или коммерческие детали.

## 4. Условия допустимости решения

Bearer-only модель запрещено использовать, если хотя бы одно условие не выполнено:

1. Токен имеет достаточную криптографическую энтропию.
2. Raw token не хранится в PostgreSQL.
3. Raw token не попадает в immutable document snapshot.
4. Raw token не попадает в service-order events, outbox или audit payload.
5. Token-bearing path исключён из обычного access logging.
6. Token-bearing URL не кешируется service worker или shared cache.
7. Публичная проекция соответствует отдельному allowlist.
8. Ссылка может быть немедленно отозвана и перевыпущена.
9. Старые версии перестают работать.
10. Print claim не выдаёт QR для revoked, expired, stale-version или hash-mismatched ссылки.
11. Cross-tenant lookup невозможен.
12. Public origin не строится из недоверенного request header.
13. QR не содержит localhost или loopback origin.
14. Invalid/revoked/expired ответы не раскрывают причину.
15. На странице нет сторонних ресурсов, которым может уйти URL через referrer.

## 5. Токен и хранение

### 5.1 Требования к bearer token

- минимум 256 бит непредсказуемого материала либо эквивалентный HMAC-derived contract;
- URL-safe представление;
- отсутствие order ID, телефона, tenant ID и последовательного номера;
- отдельный domain separation / purpose для public status;
- versioned derivation;
- постоянный защищённый `PUBLIC_STATUS_TOKEN_HMAC_KEY` либо эквивалентный секрет;
- токен нельзя восстанавливать из хеша без серверного ключа.

### 5.2 PostgreSQL

Разрешено хранить:

- link ID;
- organization ID;
- service order ID;
- token hash;
- token version;
- created/updated timestamps;
- revoked/expired timestamps;
- минимальное last-accessed поле, если оно действительно нужно.

Запрещено хранить raw bearer token.

### 5.3 Document snapshot

Snapshot может хранить только:

- link ID;
- token version;
- безопасный availability marker.

Snapshot не хранит:

- raw token;
- URL;
- QR value;
- token hash;
- публичный payload целиком, если это не обосновано отдельным immutable document contract.

## 6. Жизненный цикл ссылки

### 6.1 Создание

Ссылка создаётся сервером только для заказа текущей организации и после авторизованного employee action либо контролируемого автоматического шага при создании документа.

### 6.2 Использование

Public lookup:

- сравнивает безопасно полученный hash;
- проверяет active organization;
- проверяет revoked/expired;
- отдаёт только allowlisted projection;
- не создаёт employee session;
- не раскрывает внутреннюю причину отказа.

### 6.3 Отзыв

Авторизованный сотрудник с нужным grant может отозвать ссылку.

После отзыва:

- public lookup прекращает работу немедленно;
- queued/retry print job не получает QR;
- прежний QR остаётся физически на бумаге, но ведёт к нейтральной ошибке;
- audit receipt не содержит raw token.

### 6.4 Перевыпуск

Перевыпуск повышает token version и создаёт новый hash-boundary.

Старые версии:

- не открываются;
- не печатаются;
- не восстанавливаются из старого snapshot;
- не получают статус `READY`.

### 6.5 Закрытие заказа

Политика после выдачи требует отдельного решения.

Начальная рекомендация:

- статус может оставаться доступным ограниченный период после выдачи;
- затем ссылка истекает или показывает только нейтральный закрытый результат;
- бессрочный доступ не включается без доказанной пользы;
- гарантийные документы не добавляются автоматически в тот же boundary.

## 7. Срок действия

Для первого пилота рекомендуются два режима для сравнения:

### Режим 1 — активный заказ плюс короткий post-issue период

- ссылка действует во время ремонта;
- после выдачи действует ограниченное число дней;
- затем истекает.

### Режим 2 — до явного отзыва, но с мониторингом

Допустим только на синтетическом или ограниченном пилоте. Требует подтверждения, что долгоживущая ссылка не создаёт лишний риск.

Точное значение срока не фиксируется до pilot threat review. Слишком короткий срок создаёт поддержку, слишком длинный увеличивает окно случайного раскрытия.

## 8. Printed-paper threat model

### 8.1 Угрозы

- квитанцию сфотографировали;
- бумагу потеряли;
- QR виден постороннему;
- сотрудник отправил ссылку не тому адресату;
- старый документ распечатан после перевыпуска;
- принтер или spool содержит старый job;
- клиент переслал ссылку члену семьи;
- публичная ссылка осталась в browser history.

### 8.2 Контроли

- минимальная публичная проекция;
- отзыв и версия;
- fail-closed print validation;
- отсутствие персональных данных;
- neutral error;
- no-store;
- минимальный post-issue lifetime;
- понятная кнопка «перевыпустить доступ» для авторизованного сотрудника;
- клиентская подсказка не публиковать ссылку;
- без сторонней аналитики и ресурсов.

### 8.3 Что bearer-only не решает

Он не гарантирует, что ссылку откроет только первоначальный клиент. Это capability link, а не доказанная цифровая личность.

Поэтому bearer-only допустим только для ограниченной публичной информации. Для платежей, документов с персональными данными, подписей или спорных операций потребуется иной access model.

## 9. Rate limiting и злоупотребление

Даже высокоэнтропийный токен требует защиты от нагрузки и автоматического сканирования.

Требования:

- bounded rate per source/network window;
- bounded global rate;
- generic failure response;
- отсутствие различимых timing/error responses для разных причин;
- наблюдение за аномальным числом invalid attempts;
- отсутствие блокировки реального клиента из-за одного ошибочного сканирования;
- fail-safe, а не автоматическая блокировка всей организации без Owner review.

Rate limit не считается основной защитой секрета. Основная защита — энтропия, allowlist и отзыв.

## 10. Browser и URL hygiene

- URL не содержит персональных данных;
- URL не содержит order number как секрет;
- токен находится только в path по утверждённому contract;
- никаких query analytics parameters;
- `Referrer-Policy` ограничивает передачу URL;
- внешние ссылки открываются без передачи token-bearing referrer;
- страница не загружает внешние изображения, шрифты, аналитику и CDN;
- no-index/no-follow;
- no-store;
- токен не копируется в DOM attributes сверх необходимого маршрута;
- error tracking не получает полный URL.

## 11. Public origin

Приоритет:

1. явно утверждённый `PUBLIC_APP_BASE_URL`;
2. строго контролируемый локальный/LAN origin для пилота;
3. отсутствие QR, если безопасный origin не определён.

Запрещено:

- доверять `Host` или forwarded headers без отдельной proxy policy;
- silently fallback на localhost;
- печатать loopback URL;
- подставлять случайный LAN IP без подтверждения;
- помечать QR как READY при неизвестном origin.

## 12. Recovery и key rotation

`PUBLIC_STATUS_TOKEN_HMAC_KEY` является критическим долговременным секретом.

Требования:

- включить в защищённый backup/restore contract;
- не публиковать в Git;
- не писать в Evidence;
- не перегенерировать молча при каждом запуске;
- rotation требует явного режима;
- после rotation прежние ссылки должны быть перевыпущены или явно классифицированы как недействительные;
- UI/оператор должен понимать последствия rotation;
- backup restore должен подтверждать, что действующие QR сохраняют поведение либо контролируемо инвалидируются.

## 13. События безопасности

Разрешены события без bearer material:

- link created;
- link revoked;
- link reissued;
- print validation blocked с allowlisted reason category;
- public lookup success/failure в агрегированной форме;
- security rate anomaly.

Запрещено записывать:

- raw token;
- полный URL;
- token hash в обычный audit payload;
- публичный payload;
- клиентские данные;
- stack trace в публичный ответ.

## 14. Граница полномочий

### Сотрудник

Может, при наличии grants:

- создать доступ для заказа текущей организации;
- распечатать актуальный QR;
- скопировать ссылку;
- отозвать или перевыпустить доступ;
- увидеть точный клиентский preview.

### Владелец/управляющий

Может:

- включать разрешённые P2 public fields;
- задавать срок жизни в утверждённом диапазоне;
- видеть агрегированные метрики;
- отключить MP-001 feature flag;
- инициировать контролируемую rotation/reissue процедуру.

### Платформа

Должна неизменно запрещать P0-поля и не позволять tenant-настройке ослабить базовые security requirements.

## 15. Решение о коротком коде

Короткий код не добавляется в первый пилот автоматически.

Он возвращается на рассмотрение, если Evidence покажет одно из условий:

- документы часто фотографируют/передают посторонним;
- публичный allowlist приходится расширить до более чувствительных данных;
- владелец и клиенты принимают дополнительный шаг без заметного роста поддержки;
- threat review показывает реальное снижение риска, а не формальную «вторую защиту» на том же листе;
- появляется независимый канал доставки кода.

Если код и QR печатаются рядом, дополнительная защита считается слабой и требует отдельного обоснования.

## 16. Приёмочные тесты access model

### Token boundary

- raw token отсутствует в таблицах;
- raw token отсутствует в snapshots;
- raw token отсутствует в events/outbox/logs;
- invalid token не раскрывает различимые причины;
- token A не открывает order B;
- tenant A не может создать/изменить link tenant B.

### Revocation/version

- active current version открывается;
- revoked не открывается;
- expired не открывается;
- prior version не открывается;
- stale snapshot не печатает QR;
- HMAC mismatch не печатает QR;
- validation exception fail closed.

### Browser/network

- no-store/no-index;
- URL не попадает в service worker cache;
- внешний referrer не содержит token;
- обычный access log не содержит path с token;
- public page работает без employee cookie.

### Physical

- новый QR содержит правильный origin;
- iPhone открывает public page;
- старый QR после reissue открывает generic failure;
- документ может печататься без QR при заблокированной validation;
- интерфейс честно показывает, что QR недоступен.

## 17. Stop criteria

Bearer-only access model отклоняется или пересматривается, если:

- allowlist расширяется до персональных/юридически чувствительных данных;
- raw token появляется в хранилище или логах;
- невозможно гарантировать отзыв и version invalidation;
- print pipeline не умеет fail closed;
- публичные URL массово пересылаются и создают инциденты;
- клиенты требуют доказанного identity-bound доступа;
- срок жизни нельзя контролировать;
- security controls заметно повышают стоимость и сложность сверх ценности продукта;
- появляется более простой способ обеспечить ту же победу с меньшим риском.

## 18. Owner Gate

Перед реальным пилотом владелец должен отдельно подтвердить:

- bearer-only модель допустима для минимального P1-набора;
- срок жизни ссылки;
- кто имеет право revoke/reissue;
- видимый текст предупреждения о ссылке;
- разрешённый public origin;
- что цена, ETA и история остаются выключенными;
- что реальный клиентский пилот начинается только после DB/browser/physical Evidence.
